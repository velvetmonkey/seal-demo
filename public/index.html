The Gauntlet

A jailbroken AI agent is trying to do something dangerous. Watch its tool call get judged — gate by gate — by a decision procedure proven correct in Lean 4. Each gate stamps the call ALLOW and passes it on, or slams it DENY and destroys it. Clear every gate and it leaves as a sealed certificate.

We don't claim the model is safe. We prove the boundary is — and a theorem doesn't get jailbroken.

Under the hood — how the verdict is computed, and what is (and isn't) proven

The main stage shows you the decision. Here is the machinery behind it — deliberately kept off the hero path.

Two engines, one verdict

With the Docker container up, your call goes over MCP stdio into the actual native seal-host binary (POST /api/decide). With no backend, the same verified kernel compiled to WebAssembly decides right here in your browser. No replay, no model. Both engines are conformance-gated to return identical certs — the animation is the same either way, which is why we never show you which one ran.

What is proven, trusted, and not claimed

Proven
For a canonical action and trusted config, the combined verdict is allow iff every gating kernel allows, by the composition theorem. Axioms: {propext, Classical.choice, Quot.sound} only.
Trusted (TCB)
Lean compiler + runtime · host transport routes faithfully (fail-closed) · SealV2 canonical parser · the C ABI / FFI seam
Not claimed
model safety · classifier completeness · out-of-band effects · anything outside the MCP boundary

Seven Lean 4 kernels gate the boundary: safety, temporal, consensus, convergence, calibration, linear, budget. A call only activates the gates its config invokes — those are the gates you see on the track. Naming the trusted base is the point, not a disclaimer: a small, honest, named TCB is the entire premise of safeguarded AI.
