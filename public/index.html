The boundary is a theorem.

A jailbroken agent's tool call is intercepted and judged by a series of gates, each proven correct in Lean 4. seal doesn't trust the model — it proves whether this exact call may cross. Clear every gate and the call leaves as a sealed certificate; trip one and it's destroyed.

The agent can wrap the same call in any excuse — the boundary only sees the call.

What's proven, trusted, and not claimed

Proven
For a canonical action and trusted config, the combined verdict is ALLOW iff every gating kernel allows — by the composition theorem. Axioms: {propext, Classical.choice, Quot.sound} only.
Trusted (TCB)
Lean compiler + runtime · the host transport routes faithfully (fail-closed) · the SealV2 canonical parser · the C ABI / FFI seam.
Not claimed
model safety · classifier completeness · out-of-band effects · anything outside the MCP boundary.

Seven Lean 4 kernels gate the boundary: safety, temporal, consensus, convergence, calibration, linear, budget. A call only activates the gates its config invokes — those are the gates on the track. The verdict is computed live: the native seal-host binary (POST /api/decide, Docker) or the same kernel compiled to in-browser WebAssembly — conformance-gated to be identical. The model never runs; you supply the call, the proven decision procedure judges it.

Real verdicts from the verified seal-host (7 Lean 4 kernels). Spec layer is open; proof sources are held under the pre-award publication boundary. A demonstration, not the source.
